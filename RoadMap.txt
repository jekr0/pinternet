# HTMX + SPA Migration Roadmap (Checklist)

## 1) Цели миграции
- [ ] 1.1 Перейти на partial update контента (`<main>`) без полного reload страницы.
- [ ] 1.2 Сохранить SSR как источник истины (рендер на сервере, HTMX как транспорт/свап).
- [ ] 1.3 Обеспечить стабильные `header` и `footer` между переходами.
- [ ] 1.4 Сделать URL источником состояния (страницы, модалки, фильтры).
- [ ] 1.5 Обеспечить корректную историю (Back/Forward) без рассинхронизации UI.

## 2) URL-контракт (канонические сценарии)

### 2.1 Основные маршруты
- [x] `GET /` — лента (основная).
- [x] `GET /post/{id}` — открытие post-full.
- [x] `GET /post/create` — post-modal в режиме создания (через alias redirect на текущее состояние).
- [x] `GET /post/{id}/edit` — post-modal в режиме редактирования (через alias redirect на текущее состояние).
- [x] `GET /collections-editing` — collections-modal (особый случай, через alias redirect на текущее состояние).
- [x] `GET /profile-editing` — редактирование профиля (через alias redirect на текущее состояние).

### 2.2 Аутентификация
- [x] `GET /auth/login` — вход.
- [x] `GET /auth/registration` — регистрация.
- [x] Убрать зависимость режима auth от `$_SESSION['auth_mode']` как основного механизма URL-состояния.

### 2.3 Профиль и поиск (будущее)
- [ ] `GET /@{username}` — профиль пользователя.
- [ ] Query-параметры фильтров для шаринга/восстановления:
  - [ ] `q`, `tag`, `sort`, `page` (и другие при необходимости).
  - [ ] Поддержка фильтров на `/` и на `/@{username}`.

## 3) Серверный роутинг и рендер (PHP)

### 3.1 Разделение обязанностей роутинга
- [ ] Выделить page-routes (HTML) и action/API-routes (изменяющие операции).
- [ ] Упорядочить обработку роутов: статические -> динамические -> fallback 404.

### 3.2 Full vs Partial response
- [x] Добавить режим partial response для HTMX-запросов (`HX-Request: true`).
- [x] Для обычного запроса отдавать полный HTML-документ.
- [x] Для HTMX-запроса отдавать только целевой фрагмент (`<main>` или page-partial).
- [x] Зафиксировать единый формат серверных ответов для fragment swap.

### 3.3 Совместимость и редиректы
- [x] Добавить редиректы/алиасы со старых URL на канонические (без ломки ссылок).
- [x] Нормализовать trailing slash / без slash правила.

## 4) HTMX-навигация и History API

### 4.1 Базовая настройка HTMX
- [ ] Подключить HTMX и включить `hx-boost` для внутренних переходов.
- [ ] Определить единый target-контейнер (например, `#app-main`).

### 4.2 Стратегия push/replace
- [ ] Использовать `hx-push-url="true"` для смысловых переходов (лента -> пост и т.д.).
- [ ] Использовать `hx-replace-url="true"` для транзиентных состояний, где история не нужна.
- [ ] Формально описать, где push, где replace (мини-матрица правил).

### 4.3 Восстановление состояний
- [ ] Добавить обработчик `popstate`.
- [ ] На back/forward восстанавливать:
  - [ ] контент страницы,
  - [ ] активные модалки/панели,
  - [ ] фильтры поиска.

## 5) Frontend lifecycle (main.js + modules)

### 5.1 Эволюция App-ядра
- [x] Сохранить текущий реестр модулей и selective init.
- [x] Добавить `App.initWithin(root)` для инициализации после HTMX swap.
- [x] Добавить `App.destroyWithin(root)` для корректного cleanup перед swap.
- [x] Добавить безопасный `reinit`-сценарий для повторной подгрузки одного и того же фрагмента.

### 5.2 Интеграция с HTMX-событиями
- [x] На `htmx:beforeSwap` вызывать cleanup.
- [x] На `htmx:afterSwap`/`htmx:load` вызывать SVG preload + init модулей в новом DOM-фрагменте.

### 5.3 Устранение утечек
- [ ] Для каждого модуля добавить/проверить `destroy()`:
  - [x] очистка `setInterval`/`setTimeout`,
  - [x] снятие `window/document` listeners,
  - [x] снятие подписок на custom events.

## 6) Навигация внутри модулей (без костылей)
- [ ] Убрать прямые `window.location.href` из UI-модулей там, где нужна HTMX-навигация. (частично: auth back navigation переведена на обычную ссылку `/` без inline JS)
- [ ] Вынести переходы в единый navigation helper (push/replace/back fallback). (частично: добавлен App.nav.navigate и подключён в profile_button.js)
- [ ] Вынести общие правила открытия/закрытия overlay в единый state manager.

## 7) Модалки как URL-state

### 7.1 Post modal
- [x] Открытие create-mode: `/post/create`.
- [x] Открытие edit-mode: `/post/{id}/edit`.
- [x] Закрытие модалки -> корректный возврат URL (back или replace по правилу).

### 7.2 Collections modal
- [x] Поддержка URL `/collections-editing`.
- [x] Восстановление модалки на back/forward.

### 7.3 Profile editing modal/page
- [ ] Поддержка URL `/profile-editing`.
- [ ] Корректная интеграция с историей и возвратом в предыдущее состояние.

## 8) CSS-архитектура и унификация

### 8.1 Структура слоев
- [x] `main.css`: reset, fonts, tokens, utilities, базовые UI primitives.
- [ ] `components/*.css`: локальные стили компонентов.
- [ ] `pages/*.css`: только page-specific стили.

### 8.2 Унификация полей ввода (приоритет)
- [x] Ввести базовый класс для инпутов (`.ui-input`) и его состояния.
- [ ] Перевести повторяющиеся input/textarea/select стили на базовые классы.
- [ ] Оставить в модулях только контекстные уточнения.

### 8.3 Библиотека состояний UI
- [ ] Добавить единые utility/state-классы (`.is-hidden`, `.is-active`, `.is-invalid`, и т.д.).
- [ ] Упорядочить z-index/overlay-слои в виде токенов.

## 9) Профиль и фильтры поиска
- [ ] Реализовать профильный URL: `/@{username}`.
- [ ] Формализовать схему query-фильтров (ключи, допустимые значения, дефолты).
- [ ] Обеспечить серверное чтение и клиентское восстановление фильтров.
- [ ] Синхронизировать фильтры с history (push/replace/popstate).

## 10) Сокращение техдолга и стабилизация
- [ ] Вынести карту маршрутов/ресурсов (CSS/JS/layouts) в декларативный конфиг.
- [ ] Снизить copy-paste при подключении одних и тех же наборов ресурсов.
- [ ] Ввести единые нейминги для data-атрибутов и custom events (`entity:action`).
- [ ] Документировать контракты рендеринга и жизненный цикл модулей.

## 12) Definition of Done (DoD)
- [ ] Любой переход между ключевыми состояниями работает без full reload (кроме явно оговоренных исключений).
- [ ] Back/Forward всегда восстанавливает корректный UI и URL.
- [ ] Нет критичных утечек listeners/timers при многократных переходах.
- [ ] Повторяющиеся стили полей ввода централизованы и документированы.
- [ ] Основные URL-сценарии покрыты ручными тест-кейсами.
